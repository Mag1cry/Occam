# Occam — backend (`occ-next/`)

The backend half of [Occam](../README.md): the four-primitive kernel (Task / Executor /
Capability / Control Event) plus the gateway that judges, approves, schedules and dispatches.

It is **self-contained**: no imports from, and no runtime dependency on, any earlier
implementation (the previous `occ-os` / `occ-web` have been removed; their code stays
in git history). Everything it needs lives in `config/`, `data/`, `workspace/` and
`extensions/`.

## 当前能力与边界

- Four control-plane primitives: Task, Executor, Capability, and Control Event.
- Fixed core commands with SQLite persistence.
- Task IDs are generated by Core during `create_task`; Web and other callers
  receive the returned ID and use it for all subsequent commands.
- No public `Execution` object or execution table; the Task remains the stable control object while the Worker and LangGraph checkpoint stay outside Core.
- Tools can be configured with different approval requirements; executor `tools_from` is an allowlist,
  and `tighten` can add approval requirements but cannot remove them.
- The LangGraph Agent is a **managed executor**: Occam starts it in a Worker subprocess, and its
  tool requests pass through the gateway permission and approval pipeline. Its adapter reads the
  managed executor's result and audit from its checkpoint store.
- Model providers are declared one per file under `extensions/_providers/`; executors reference
  a provider and model. API keys are referenced by environment variable and never enter Task,
  events, hashes, or UI.
- Executor manifests can expose safe selectable runtime parameters such as temperature,
  max tokens, and top-p. The browser submits only selected values; Core still stores
  only `executor_config_ref`.
- External extensions live under `extensions/<extension-id>/manifest.yaml`, outside
  `src/`. Each package owns its directory and its single `manifest.yaml`, and that
  manifest declares any mix of `tools` / `executors` / `schedules` / `providers`
  (the package itself has no type). Shared executor settings can be placed in
  `defaults`. Providers and schedules are one file per entry under `_providers/`
  and `_schedules/`; a workspace-level `workspace.yaml` or other aggregate manifest
  is not supported. Allowed Worker tool requests go through the permission pipeline and are
  accounted by the kernel before execution; requests that fail gateway authorization are denied.
- **Writing a package**: [extensions/AUTHORING.md](extensions/AUTHORING.md) is the
  author-facing tutorial (manifest table, the worker contract, and the mistakes that
  get a package rejected). [extensions/README.md](extensions/README.md) tells you what
  the directory looks like. A package can declare tools and executors together; providers and
  schedules remain separate declarations under `_providers/` and `_schedules/`.
- Scheduling and dispatch live under `src/tasks/`, not a separate automation module. See
  [the tasks overview](src/tasks/README.md) for scheduling and Worker lifecycle.
- The planned external read-only monitoring mode is a separate integration path. A future
  LangGraph monitoring sample will observe an Agent started outside Occam; it does not reclassify
  the current managed LangGraph executor. Its adapter/event contract is not implemented yet.
- OCC control state, LangGraph state, and Controller lifecycle state are separate;
  the defaults are `data/occ-next-v1-control.sqlite`,
  `data/occ-next-v1-langgraph.sqlite`, and `data/occ-next-v1-controller.sqlite`.
- `Task.session_ref` is the immutable LangGraph `thread_id`. LangGraph owns
  messages, graph position, interrupts, and checkpoints; OCC stores only the
  opaque `checkpoint_ref` supplied by the TaskController.
- The workbench starts one child process per Task so cancellation can
  terminate the actual Agent process. This is a concrete web controller, not
  a second runtime abstraction.

The three integration depths and their design intent are recorded in
[extensions/AGENT_INTEGRATION_DECISION.md](extensions/AGENT_INTEGRATION_DECISION.md); implementation status belongs here
and in the extension documentation.

## Development

```powershell
uv sync --extra dev --extra agent
uv run pytest -q
uv run occ-next                                          # 按配置启动（默认 127.0.0.1:8765）
uv run occ-next --reload                                 # 开发时监视源码并自动重启
```

`occ-next` is registered in `[project.scripts]`; `uv run` executes it in the project environment.
Reload still serves the app through the Uvicorn factory, so importing the module does not assemble
the system or start its scheduler.

The production call chain is `web/http.py -> gateway/facade.py -> tasks/controller.py ->
tasks/spawn.py -> LangGraph Worker -> tasks/channel.py -> core/kernel.py ->
gateway/function -> extensions/tools.py`. Web never owns a process handle, Worker never
opens the OCC control database, and a tool call is judged and accounted by the kernel
before it executes.

### Release: one process, one port

Two shapes, and the only difference is whether the built frontend is mounted:

```powershell
# 开发形态：界面归 vite dev（5173，带热更新），后端只管接口
cd occ-command-center ; npm run dev
cd occ-next ; uv run occ-next                           # 接口在 127.0.0.1:8765

# 发布形态：**同一个进程把界面和接口一起端出来**
cd occ-command-center ; npm ci ; npm run build          # → dist/（这一步需要 Node）
cd ../occ-next
$env:OCC_NEXT_WEB_DIR = "../occ-command-center/dist"
uv run occ-next                                          # → http://127.0.0.1:8765/
```

The backend sends **no CORS headers** unless you name an origin (the UI is expected
to be same-origin with `/api`), which is why the release shape serves the built
frontend from the same process instead of pairing it with a reverse proxy.
`OCC_NEXT_WEB_DIR` unset means nothing is mounted — that is the dev shape, and `/`
is then a plain 404. A UI served from *elsewhere* needs `OCC_NEXT_ALLOWED_ORIGINS`
(see "Serving beyond this machine").

**Releasing means replacing the code, never the data.** The three things that are
yours live outside it: `data/*.sqlite` (kernel, launch log, dispatch log, gateway
audit, access token), `workspace/` (task bodies), `extensions/` (your packages).
The store migrates itself on open (`PRAGMA user_version`; a database *newer* than
the code is refused rather than written to), so an upgrade is: pull, rebuild the
frontend, restart. Back up by **stopping first** and copying `data/` + `workspace/`
— the SQLite files are in WAL mode and a copy taken while running can be half a file.

### Where credentials live: `config/.env`

Two directories, two owners — mixing them makes "back it up" and "edit it" two faces of
the same thing:

| directory | written by | holds |
| --- | --- | --- |
| `data/` | **the program** | kernel database, launch/dispatch logs, gateway audit, access token, link secret |
| `config/` | **you** | this machine's secrets and run parameters |

```ini
# occ-next/config/.env        (not in git — `config/` is ignored)
OCC_NEXT_FEISHU_APP_ID=cli_xxx
OCC_NEXT_FEISHU_APP_SECRET=xxx
OCC_NEXT_FEISHU_OPEN_ID=ou_xxx
```

It is read **by the entry point** (`serve.py::main`, before assembly) and it
**never overrides a variable that is already set**: an ad-hoc `$env:OCC_NEXT_HOST='0.0.0.0'`
always wins, so a debugging override is never silently beaten by the file.

**The file is not the contract — the environment is.** A package only ever reads
environment variables (providers name theirs with `api_key_env` in the manifest; the
Feishu channel reads `OCC_NEXT_FEISHU_*`). `config/.env` is just one way to fill the
environment; systemd, Task Scheduler, or a start script are peers of it.

### Serving beyond this machine

**The LAN needs no credential; anything outside it does.** Anything reachable
from the internet can start processes on this machine (`mcp.register` hands its
payload straight to `Popen`), so the boundary is the point.

```powershell
uv run occ-next --host 0.0.0.0 --no-proxy-headers
```

- **`--no-proxy-headers` is not optional.** uvicorn defaults to trusting
  `X-Forwarded-For` from loopback; with any reverse proxy on `127.0.0.1` the
  client address becomes attacker-influenced and the LAN check can be spoofed.
  With the flag, `request.client.host` is always the real socket peer.
- The token lives in `data/access-token.json` (generated on first start,
  reused after; the directory is git-ignored). Set `OCC_ACCESS_TOKEN` to
  override it — useful where writing secrets to disk is not an option. **Read it
  on this machine**: that is what "local authentication" means.
- Credentials travel as **`Authorization: Bearer <token>`**, or as `?token=` on
  the SSE stream, which cannot carry custom headers. **There is no HTTP Basic
  support** — a browser will not prompt for a `Bearer` challenge, so a remote
  client has to hold the token itself rather than lean on the browser.
- `OCC_TRUSTED_NETWORKS` narrows what counts as "LAN" (comma-separated CIDRs,
  default loopback + RFC1918 + link-local). Narrowing it to `127.0.0.1/32` is
  the way to exercise the external path from this machine.
- **CORS: nothing is added by default, so there is no `*`.** A UI served from
  the same origin as `/api` needs nothing. A UI served from *elsewhere* — an
  Android build, where the WebView serves the bundle from `https://localhost` —
  names its origin explicitly:

  ```powershell
  $env:OCC_NEXT_ALLOWED_ORIGINS = 'https://localhost'     # 逗号分隔，逐字比对
  ```

  Entries must be bare origins (scheme + host + optional port, lowercase, no
  path); anything else raises at startup and names the offending entry, because
  a typo'd list is fail-closed but shows up as an opaque browser CORS error.
  The allowance is scoped to `/api/` and performs **no permission check** — an
  unauthenticated request is still 401, and an unknown path is still 404.

  **Do not reach for `*` here.** The LAN is trusted by source address with no
  credential, so a wildcard would let any web page the user visits drive
  `POST /api/command` as a trusted caller — and `mcp.register` hands its payload
  to `Popen`.

The checked-in `extensions/_providers/deepseek.yaml` and
`extensions/_providers/uniapi.yaml` contain non-secret model catalogues; set
`DEEPSEEK_API_KEY` or `UNIAPI_API_KEY`, then open
`http://127.0.0.1:8765`. Add another provider as one more file in `_providers/`,
and so on. The real model smoke test is opt-in;
normal tests never call the network.

Provider model catalogs can be refreshed with the scripts under `scripts/`:

```powershell
uv run python scripts/update_deepseek_models.py
uv run python scripts/update_uniapi_models.py
```

Set `DEEPSEEK_API_KEY` or `UNIAPI_API_KEY` before running. Each script calls
the provider's OpenAI-compatible `/v1/models` endpoint and updates only that
provider's executor manifest. The `catalog` URL is separate from the model
inference URL, and existing matching profile UI/runtime settings are kept.

Scheduled task definitions are declared in `extensions/_schedules/`; the scheduler materializes
each occurrence as a Core Task. See [the tasks overview](src/tasks/README.md) for the current model.
