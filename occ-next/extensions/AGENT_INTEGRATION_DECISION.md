# Agent 集成决策

本文只记录决策及其意图。当前实现与待办状态见 [`../README.md`](../README.md)、
本目录其他扩展文档和仓库根目录的项目说明。

## 决策

Occam 将 Agent 集成分为三档，按 Occam 对执行生命周期与运行时的控制程度区分：

1. **托管执行**：Occam 创建并管理 Worker 生命周期；Worker 发起的工具调用进入 Occam 权限与审批管线。
2. **外部执行控制**：Agent 运行时在 Occam 之外；Occam 通过外部服务接口启动、查询或控制执行。
3. **外部只读监控**：Agent 完全由外部系统运行；Occam 读取其运行记录并提供观察视图，不控制 Agent，也不代其作出权限判决。

当前 LangGraph Agent 属于第一档。未来可提供一个第二套 LangGraph 样例，作为第三档的外部监控扩展：样例监控由外部启动的 LangGraph Agent。框架名称相同不代表集成深度相同，二者是不同的运行实例与接入路径。

## 设计意图

- **控制与观察分开**：托管执行可强制工具请求经过 Occam；只读监控只能报告来源系统提供的证据，不得将观察结果标记为 Occam 的授权、审批或执行事实。
- **统一呈现而不抹平差异**：外部来源映射到共同的任务、对话与工具活动视图，同时保留来源标识、原生引用、时间与证据依据。无法可靠映射的字段保持未知，不猜测或伪造。
- **由 Occam 定义规范模型，由适配器处理来源差异**：统一事件与执行流模型是 Occam 的产品契约；来源专用 SDK、解析库或查询方式可以复用，但不把某个框架的内部数据结构或通用观测库直接变成内核契约。
- **先采用来源原生证据，再做显式映射**：适配器可以读取框架 checkpoint、事件回调或运行记录；每种来源说明其覆盖范围、缺失字段、时间语义与读取限制。外形统一不代表证据完整度相同。
- **扩展承接适配复杂度**：不同 Agent 框架的数据模型、生命周期、持久化和控制能力由扩展适配；内核不依赖某个 Agent 框架，也不假设只读监控等同于托管执行审计。
- **授权以实际执行边界为准**：工具白名单与审批策略由 Occam 在托管工具通道执行；对完全外部运行的 Agent，除非另有受控代理通道，监控扩展不能声称实施了这些限制。

## 适配策略

规范化边界由 Occam 自己维护；来源读取尽量使用 Agent 框架公开、稳定的数据接口。引入第三方库的前提是它确实降低某个来源适配的维护成本，且不会隐去来源差异或错误地声称统一保证。当前不预设一个通用库能解决所有框架的数据归一化，也暂不绑定具体库。
