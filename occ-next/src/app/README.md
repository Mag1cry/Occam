# app/ — 装配

构造并连接上面全部。**只有这一个地方 new 具体实现。**

| 文件 | 装什么 |
| --- | --- |
| `build.py` | 唯一的依赖装配根 |
| `settings.py` | 环境变量与默认路径 |

## 边界

- 不做业务判断。这里的每一行都应该是"建什么、接给谁"。
- 依赖方向：装配 → 全部；全部 → 不反向 import 装配。
- **存储在这里决定一次**，之后绑进 `core/kernel.py`——外围（gateway / tasks / web）
  拿不到它。
- **四个列表也在这里建一次**——能力、执行者、供应商、日程，之后绑给需要的人。

## 装配期建的两样"全局只有一份"

| 建什么 | 为什么在这儿 |
| --- | --- |
| **存储** | 决定一次，绑进 `core/kernel.py`；别处拿不到它 |
| **四个列表** | 用哪个实现、接到哪，"只有一份"这件事在装配期定死 |

**都不是 `import` 一个全局变量。** 理由不是洁癖：测试需要一个**干净的例子**，而全局
变量得手动清理，忘了就串味。而且"拿到它"应该是一步看得见的事。

## 填一份"完整的现在"，不是"改了哪几条"

加载器（`extensions/hotload.py`）**不 import 网关**，所以这里给它一个写入面
（`_Registrar`）：它交出一份完整的 `Loaded`，写入面转手填进四个列表和供给表。
回滚就是把上一次那份**原样再交一遍**——不用维护一份"我刚加了什么"的账，
而那份账正是会跟真实状态漂移的东西。

顺序有讲究：**先填列表、再换供给**。反过来的话，有一个瞬间能力列表说的是新的一份、
而点下去调的是旧的那一份。

## 启动顺序里有一件事不能少

**先对账，再让任何东西起得来。** 后端被杀时子进程会活下来，而重启之后"哪些 Task 还在跑"
只能靠启动记录重建——晚一步就会起第二个写者（两个进程写同一个 checkpoint）。

## 那个真环怎么破的

调度器要建 Task（派发），门面要触发调度器（`schedule.trigger`）——**两边互相要**。
断在调度器那一侧：它收一个 `Dispatcher` Protocol（`tasks/scheduler.py`），而那个 Protocol
由门面的 `TaskDispatch` 实现。于是构造顺序是 内核 → 控制 → 派发 → 调度器 → 门面，
**没有一处回填**。
