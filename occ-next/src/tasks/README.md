# tasks/ — Task 怎么开始、怎么跑、怎么收尾

内核产生 Task，但它不能运行任何东西。这里补上那一半：**什么时候触发**、起进程、传 IPC、
收报告、对账。

> 名字说明：`core/task.py` 是 **Task 原语本身**（委托、控制状态、外部引用，是数据）；
> `tasks/` 是**围绕一次委托发生的全部机制**。两者不互相 import——前者不知道进程存在。

| 文件 | 装什么 |
| --- | --- |
| `scheduler.py` | 按 cron 派发 + **派发记录**（同一 occurrence 只派发一次） |
| `controller.py` | 持有 Worker 句柄、听 IPC、提交内核命令 |
| `reconcile.py` | 重启对账：读启动记录、探 pid、把 Task 标成"待对账" |
| `spawn.py` | 组装启动参数 + 起停进程 |
| `bootstrap.py` | spawn-safe 的 Worker 入口（**宿主提供，但跑在子进程里**） |
| `channel.py` | IPC 协议 + **包作者要照着写的契约** |
| `probe.py` | 判断历史记录里的进程还活着吗（防 pid 复用） |
| `launches.py` | Worker 启动记录——**对账的依据**，不是观测 |
| `inputs.py` | 任务正文的外部读取 |

## 边界

- **不判决**。判决在网关（`gateway/function/`）。
- **不改状态**。改状态走内核的迁移通道，这里只提交固定命令。
- **不调用工具**。工具调用走 `gateway/function/pipeline.py`——`controller.py` 那一侧
  **不 import 内核的 `CallFunction`**，也不知道判定有哪几种：它只知道"把请求交给管线，
  把答复原样发回去"。
- **不处置它没持有的进程**。重启后看见历史记录里的 pid 只探测、不杀：pid 会被复用，
  杀错不可撤销。探测到活着只标"待对账"，由人决定。
- **派发失败必须留痕**，否则「从来没跑过」和「跑了但失败了」在界面上长得一模一样。

## 「看得见」和「做得了」是两件事

发给 Worker 的是一份工具清单；判决在网关另做一遍。**两件都要有，缺一不可**：

| | 谁定 | 回答什么 |
| --- | --- | --- |
| 清单 | `tools_from`（执行者声明了用哪些供给） | Worker **看得见**什么 |
| 判决 | 网关 + 审批地板 | 它**做得了**什么 |

清单决定它看得见什么，判决决定它做得了什么。**只有清单**等于把边界交给 worker 自觉；
**只有判决**等于它连自己要调的东西都不知道存不存在。

## 为什么日程在这里

**日程本质上就是"定时 + 多 Task"**——它是 Task 的一种触发方式，不是独立领域。
定义在 `extensions/_schedules/<name>.yaml` 里，开关也在那里。这里只剩派发。

日程自己的规则只有两条：**occurrence 幂等**（同一个 `schedule_id + 分钟` 只能派发一次），
加上**一条坏日程不能挡住同一分钟里的其它日程**。就这么点规则，撑不起一个顶层目录。

**它是轮询，不是定时。** 每 30 秒醒一次看有没有到点的。occurrence 幂等让轮询是安全的，
而算"下一次该在几分几秒醒"要维护一堆状态——轮询更简单，代价是最多晚 30 秒。

## 执行者只有一种：一个入口函数，被跑一遍

没有"轻的"和"重的"两种形态。包作为执行者时，它的**入口函数被跑一遍**——而那个"跑"
就是这里起的进程。所以这个目录的每个文件都服务**所有**执行者，没有岔路。

**唯一的分叉在终态**，而那只由"怎么退出的"决定：

| 它说什么 | 那是什么意思 | Task 落到哪 |
| --- | --- | --- |
| `completed_report` | 正常退出，结果取**最后一次的输出** | `succeeded` |
| `interrupt_report` | **我停下来等审批** | `paused` |
| `failed_report` | 其他任何异常 | `failed` |

**左列是"它怎么说"，右列是"那意味着什么"——两套词，别混。** `interrupted` 只在左列活着。

**"出错由 Task 主管"**——执行者只说"我是怎么结束的"，至于那意味着什么终态，
是这一层的事（映射表在 `controller.py`，词表在 `channel.py`）。

### 结果不在内核，在执行者的包里

**内核只存 `result_ref`**（ADR-008 有意不存返回值）。结果本身**归执行者的包**：
它自己存、自己答。

- **跑 LLM 的**：checkpoint 是 LangGraph 自己保留的；包提供一个**查询函数**，
  前端靠它做审计（`adapter` 的 `read_result` / `read_audit`）
- **不提供查询函数的**：它的结果就是**短命的**——跑完在宿主内存里，重启就没了

**这不是缺陷，是分工**：内核凭什么替一个它不认识的执行者决定结果存哪、存多久？

## 一次 Task 的运行

一个进程 + 一条 IPC + 一份退出报告。这三样加起来的失败模式（启动失败、异常退出、被杀、
孤儿、pid 复用）就是这里的大部分文件；它们不该和执行者是什么混在一起——后者是
`extensions/` 和 `gateway/directory/executors.py` 的事。

## 一张表跟着它唯一的读者走

`dispatches` 表只有 `scheduler.py` 读写 → 它就住在 `scheduler.py` 里。
`worker_launches` 有两个读者（`controller.py` 写、`reconcile.py` 读）→ 它单独立一个文件。

**一条表跟着它唯一的读者走；有多个读者的才单独立文件。** 不按"都是 SQLite"堆在一起——
那正是杂物抽屉的起点。

## 重启对账为什么这么小心

后端被杀时，非 daemon 的 worker 子进程会活下来；重启之后内存里的句柄全没了，只有
`launches.py` 里的 `process_id` 和 `started_at` 还留着。重建这个判断是**「不给同一个
Task 起第二个 worker」**的前提。

**为什么是探测而不是杀掉**：一个控制器不能处置它从未持有的进程，而且 pid 会被复用——
按 pid 直接杀有可能杀掉一个无关进程，那个动作不可撤销。所以探测的结论只用来把 Task
标成"待对账"并挡住重复启动；**真正要不要处置由人决定**。

**误报的方向要选安全的**：拿不到创建时间时就保守地判"可能活着"，代价是该 Task 需要
人工确认一下，而不是悄悄起第二个写者。
