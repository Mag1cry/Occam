## 两条规则

1. **目录用名词**，用你已经在说的词——不是角色名。
   判断标准：打开目录之前，你能不能说出一句「它装的是哪些东西」。
2. **每个目录一个 README**，重点写**不装什么**。边界比内容更能说明一个目录是什么。

   骨架固定，每份都一样：

   ```markdown
   # <目录> — <一句话：它装什么>

   <一段：它为什么独立 / 它的章程>

   | 文件 | 装什么 |
   | --- | --- |

   ## 边界
   <不装什么>

   ## <这个目录自己的论题，零到若干节>
   ```

   **边界紧跟在文件表后面**——它是这份 README 里最该被读到的一段。
   历史叙述（"以前是 X，现在改成 Y"）不收在各目录里，统一放在本文件的
   [这一轮推翻了什么](#这一轮推翻了什么)；**缺陷与欠账**放在 [`OPEN_ISSUES.md`](OPEN_ISSUES.md)。

## 一眼树

```text
core/          内核：四原语 + 控制事件。不运行、不做 IO、不判决
gateway/       网关：判决在这里（两半）+ 四个列表 + 门面 + 记录
  permission/    公用：谁在请求、判成什么
  access/        对外界：谁能进来          （网关自己判，不经过内核）
  function/      对工具执行：能不能跑       （判决在这里，内核只记账）
  directory/     **四个列表**：能力、执行者、供应商、日程（全局只有一份）
  facade.py      命令分派
  audit.py       审计流水与事实流游标
extensions/    声明：一套。**一切注册都在这里**——包（工具 / 执行者；智能体也是执行者）
  _schedules/    日程：一条一个文件
  _providers/    模型供应商：一家一个文件
tasks/         Task 怎么开始、怎么跑、怎么收尾：日程触发、进程、IPC、报告、对账
               工具调用不在这里——它走 gateway/function/pipeline.py
web/           网页接入：HTTP、只读投影、事实流；**配置舱**（前端主视图）
storage/       内核控制库
app/           装配
serve.py       把它跑起来（给 uvicorn 的工厂 + 命令行入口）
```

`extensions/` 是**唯一一条供给侧**，而**宿主不认识任何一个包**——没有"包类型"表，
没有"工具名 → 实现"的工厂表。加一个包不改宿主一行代码。

**工具有两种供给，不硬统一**：外面已经在跑的 MCP 服务器（`url`，只连不碰），
或包里一个 Python 对象（`entrypoint`——注册时**实例化一次成为单例**，它的函数就是工具，
调用就是一次普通函数调用，不走 MCP 也不起进程）。

**而工具的句柄不归供给方**：它归 Capability 这一线，**由 gateway 发出去**——
句柄如果由供给方递出来，谁拿到谁就能调，判决就被绕过了。所以包作者和 agent 作者
看到的永远是"一堆函数"，进程和协议藏在后面。

**同一个事实，两套视图**——因为它们服务两种读者：

| 视图 | 按什么组织 | 谁读 |
| --- | --- | --- |
| **注册表**（`gateway/directory/` 那四个列表） | 按**类型** | 后端判决、起 worker、派发 |
| **配置舱**（前端主视图，`web/snapshot.py`） | 按**声明文件**（包 / 独立文件） | 人 |

**后端从不问"这属于哪个包"**，它只问"这个工具存在吗"、"这个执行者允许用它吗"。
而配置舱问的正是前者——所以它是**投影**，不是第五份数据。

一个函数可以**同时是工具和执行者**（作为工具被**调**、作为执行者被**跑**）。声明上它是
两条，**缝起来的是名字**——所以"执行者写全名"不只是好读，它是把这一个东西的两半拼上的
那根线。详见 `extensions/README.md`。

## 判决与记账分家

| 问题 | 谁答 | 在哪 |
| --- | --- | --- |
| 谁能进来？ | **网关** | `gateway/access/` |
| 有哪些工具？要不要批？这个执行者收紧过什么？ | **网关** | `gateway/directory/` + `gateway/function/` |
| 这次调用准了吗？谁批的？ | **内核记账** | `core/capability.py` + `core/event.py` |

**内核不知道有哪些工具**，也不再回答"要不要批"。它收到的是"这次调用，判定是 X"。

**两处判决都默认拒绝，规则只声明允许**（`gateway/permission/judge.py`）。

**"能不能调"和"要不要人批"是两件事，分两步走**：先判能不能（allowlist，默认拒绝），
再按**显性声明**的审批要求定性成 `allow` 或 `needs_approval`。塌成一个布尔值就分不出
"不许"和"还没问"——而 `approval_required` 是**必填**的，没有"默认不用批"这回事。

**"Agent 不能伪造批准"这条性质没变，守卫换了人**：判决仍然发生在**宿主进程**里（网关），
Worker 在另一个进程碰不到它。今天这条由内核保证，明天由网关保证。

## manifest 是唯一事实

**没有配置状态库，也没有例外。** 一个东西是什么、开不开、什么时候跑，只在**它自己那张
声明**里说——包是 `extensions/<id>/manifest.yaml`，日程和供应商是各自那个文件。

清单有**两层**：

```yaml
id: weather                   # ← 包层：这个包叫什么、开不开、共享的底座
enabled: true
name: 天气
defaults: {...}               # 包里所有条目共享（只服务 executors）

tools: [...]                  # ← 条目层：每条写明 type，type 决定必填项
executors: [...]
```

| 层 | 必填 | 可选 |
| --- | --- | --- |
| **包层** | `id`（包的唯一名字，**唯一性只在这一层判**） | `enabled`（默认 true）· `name` · `description` · `version` · `defaults` |

**条目层有哪几类、每类必填哪些栏——那张契约表在 `extensions/README.md`，只有一份。**
四类走同一张表，但**容器两种**：`tools` / `executors` 住在包清单里；`schedules` /
`providers` 各自**一条一个文件**（`extensions/_schedules/`、`extensions/_providers/`，
它们没有包层）。

**为什么那两类独立**：它们的干货是**数据**（什么时候跑 / 怎么连 + 一张模型目录）。
装在包里要连带背一个用不上的包结构，而且**一个写错就毁掉整个包**。

**清单上没有 schema、没有工具名。** 工具的 schema 全部来自**供给方**：外面那台是
`tools/list`，包里那个是**读单例有哪些函数**。今天那几格要写两遍（清单一遍、provider
一遍），再断言两边相等——现在只有一个来源。

**连"用户在界面上创建的东西"也是写文件**：新建智能体 = 写一个新包目录 + 清单；
**新建一条日程 / 加一家供应商 = 各写一个文件**。

用户把一个东西设为 off = **把它那张声明里那行改成 `enabled: false`**，走
`extensions/writer.py`（写前校验 + 原子替换）。这是破坏性改动：没有撤销、没有版本、
没有 diff 门槛（ADR-033）。

所以**声明只有一个来源：`extensions/` 下的文件**。而**包没有类型**——清单上注册了哪
几条、各是什么 `type`，它就是什么；"这是个什么包"是从清单里读出来的结果，
不是写进去的前提。详见 `extensions/README.md`。

### 登记与加载是两段，禁用的东西也在列表里

**扫描 = 登记，加载 = 可用。只有被破坏的包才禁止注册和使用。**

**为什么关着的也要登记：前后端用同一份事实。** 那四个列表**就是前端渲染的依据**——
关着的包不进列表，前端就只能自己另编一套"关着的扩展"的概念，于是同一件事又变成
两处在说。关着的它在列表里答"已下线"，前端照常渲染，只是点不动。

四行状态表见 `extensions/README.md`。

### 扩展更新：开关即时生效，源码修改后重启

改 `enabled` 后走一条固定路径：重读所有声明 → 加载当前启用项 → 一次替换四个列表。
不做逐包增量更新，也不提供重新识别 Python 源码的按钮。单个扩展加载失败仍记诊断并隔离；
列表整体替换失败则恢复上一份列表，避免留下半次更新的状态。

修改扩展 `.py` 文件后重启宿主进程——**没有"重新识别"按钮**（理由见
`extensions/README.md`：换取它的是一整套模块卸载，而那一格用重启解决）。
开关关闭后，不再使用该扩展的工具；此前导入的 Python 模块留在宿主进程，直到重启才彻底卸载。
正在运行的 Worker 仍可继续；它后续发起的工具调用会按当前列表重新判决，已下线的工具会被拒绝。
启动时已禁用的扩展仍不会被 import。

### 复杂度减法的边界

**做了减法的地方**：只服务源码热替换的模块卸载（整个删掉）、手写的 MCP 协议（换成库之上的
薄适配层）、`Supply` 的来源子类（合成一个数据对象）。

**没有减的地方**：工具授权绑定请求指纹、事件链损坏检测、声明写入校验与原子替换、
单扩展故障隔离、Worker 重启对账。它们分别保护授权、控制事实、声明完整性和进程生命周期——
**简化结构不该动这些**。

MCP 只支持项目实际采用的 HTTP 传输（stdio 那条路没有搬：宿主不起子进程），
超时、协议错误和连接关闭仍由适配层明确处理。

### 引用怎么读：重读，读不到就是不存在

状态一律来自对象**重读**（ADR-031）。**没有墓碑。**

| 态 | 什么时候 |
| --- | --- |
| 可解析 | **声明里写了**，而且加载成功、现在可用 |
| 已下线 | **声明里写了，但当前不可用**：`enabled: false`，或加载失败 |
| 未知 | 声明里没有——含读不出来/校验不过的，它从来没被承认过 |

禁用的东西会答"已下线"而不是"未知"，因为它在声明层已经登记了。
这个区别必须说得出来：一个能说清原因，一个只能承认不知道。

## 四个原语

| 原语 | 在哪 |
| --- | --- |
| Task | `core/task.py` —— 委托、控制状态、外部引用 |
| Capability | `core/capability.py` —— **所有函数调用的审计记录** |
| Executor | `core/executor.py` —— 一根稳定引用 + Task 怎么绑定它 |
| Event Chain | `core/event.py` —— 控制事件类型与不可变事实 |

执行者的**定义**（worker 入口、prompt、模型）不是原语，是供给：由 `extensions/executors.py`
从声明造，登记在 `gateway/directory/executors.py`。

**工具更薄**：内核这边只有"这次调用，判定是 X"这一条审计记录。工具长什么样、在哪个
进程里跑，它一概不知道。

**内核只存两样东西**：Task 和事件。待审批的那几格长在 Task 上，审计记录长在事件链上——
所以 Capability 和 Executor 两个原语**没有自己的表**。Port 和命令也都跟着原语走，
只有真正共用的两样（`store.py` / `errors.py`）不是。细节见 `core/README.md`。

## 目录粒度分析

判据不是文件数，是**边界**：① 能被一句话说清（说的是东西不是角色）；② 有**自己的规则**；
③ 删掉它那条规则就无处安放。

按这三条查，7 个顶层目录全部成立。被这条判据筛掉的五个：`builtin/`、`config/`、`devices/`、
`mcp/`，以及**顶层**的 `schedules/`——每一条都是这条判据自己判出来的（理由见下）。

（`schedules/` 后来以 `extensions/_schedules/` 回来了——**它不是代码目录，是声明文件**，
跟"日程的机制该不该占一个顶层目录"是两回事。）

## 这一轮推翻了什么

| 原来说 | 现在 |
| --- | --- |
| ADR-006 / 027 / 038：「Core 是唯一裁决者」，Core 合并审批地板与执行者范围并执行 | **判决搬到网关**，Core 变成记账者。守卫换了人，性质没变 |
| ADR-028：开关存在配置状态里，manifest 的 `enabled` 只在对象首次出现时作种子 | **manifest 是开关的唯一事实**，没有配置状态库 |
| 「内置能力」是一档：两个只读工具由代码直接注册，**没有 manifest、界面上看不见、也关不掉** | **取消这一档**：五个只读工具合成一个检入的包 `extensions/workspace/`，实现就在包里（`builtin/` 因此消失） |
| 包有类型：`capability` / `executor` / `ability` / `mcp`，三条加载路径各自维护，其中两条互相禁止对方 | **包没有类型**，一个加载器读一份清单；`weather` 不再需要 `type: ability` 才被允许两个都声明 |
| 「哪些栏必须有」散在三个加载器的 `if` 里，从来没有一处说过 | **一张契约表**：`type → 必填项`（`extensions/manifest.py`）。`type` 显式写，必填项挂在它上面 |
| 工具的实现有两条路：`kind` 决定走包内文件还是走宿主里的一张工厂表 | **两种供给，不硬统一**：`url`（外面在跑的 MCP 服务器）或 `entrypoint`（包里一个对象，实例化成单例）。`kind` 消失 |
| 工具的 schema 写两遍：manifest 一遍、provider 的 `manifest()` 一遍，再断言两边相等 | **只有供给方一个来源**——外面问 `tools/list`，包里读单例有哪些函数。没有可断言的东西 |
| 工具句柄由扩展实现（`CapabilityProvider`） | **句柄归 Capability 这一线，由 gateway 出去**——但**藏不藏不是安全**，安全靠进程边界；绑 schema 字典而不是绑 stub，则是**框架手里根本没东西可跑** |
| `executor_type` 由宿主维护白名单（`SUPPORTED_EXECUTOR_TYPES = {"langchain-agent", "weather"}`） | 删掉。它校验的是一个**宿主自己从不使用**的标签 |
| `allowed_parameters` 与 `defaults` 各写一遍（默认值一遍、范围一遍） | **一份 `parameters` 声明**：默认值 + 范围 + 标签。界面拿它渲染控件，worker 拿解析后的值 |
| 一个包里有 N 条 executors，N = 模型数 | **模型在配置里选**。错的不是"一包两条"，是**一个本该是配置的维度被抬成了身份** |
| ADR-024：「已下线」要有墓碑（配置状态里留一行） | 声明层已登记，**禁用的东西自然答"已下线"，不需要墓碑** |
| 设备、MCP 是独立外围：MCP 是扩展的**一种**，工具还能走包内端点 | **两种供给分清了**：外面是 MCP（只连），包内就是一个对象（直接调函数）。`devices/` `mcp/` 因此消失 |
| 智能体是用户创建的配置，存在库里 | **智能体就是配置后的执行者**——同一个清单、同一个列表，只是写 `executor:` 而不是 `worker:` |
| 日程的定义与开关存在库里 | **日程在声明里**；它是"定时 + 多 Task"，所以派发归 `tasks/`（**顶层** `schedules/` 因此消失） |
| 日程跟着扩展包一起声明（装在包清单里） | **日程一条一个文件**（`extensions/_schedules/<name>.yaml`）——炸的范围小、好改，而且不必回答"包被禁用时它带的日程算什么" |
| 模型供应商只是执行者条目里的一个字符串 | **供应商是独立的声明 + 独立的列表**（`extensions/_providers/`）——它的干货是数据（怎么连 + 模型目录），装在包里要背一个用不上的包结构 |
| agent 把工具绑成可执行的 stub 给模型 | **绑 schema 字典**：框架手里根本没有能跑的东西，执行权 100% 在 Worker 手里 |
| `SetSubjectState`：执行者的在线/离线/故障进事件链 | **整个删掉**——它没有调用者，而且"它现在是活的"是**观测**，不该写进那个不可删的东西 |
| 命令有幂等：`command_results` 表 + 每个命令一个 `idempotency_key`，命中就回缓存 | **整个删掉**（`core/store.py`）。挡重复提交的是**状态机的前置条件**；认出"这不是新请求"的是**请求指纹**（`core/capability.py` 规则一/二）。顺带修掉三个 bug：键是**全局**的会跨 Task 命中别人的结果、replay 返回的是**第一次那组 id**、`interrupt` 的键漏了 `tool_id`（换个工具再打断被当成重放） |

**赚到的：** 删掉一个库、一个模块、三个概念（`seed` / `seed_value` / `source`），
以及两条反直觉的规则——"改 manifest 的 `enabled` 对已出现的对象无效"、
"暂停一条日程会在重启后自己回来"。

- **五个只读工具要合成一个包**（`extensions/workspace/`），改成一个 `entrypoint`。
  两个旧包的 id 消失，引用它们的 `tools_from:` 要跟着改。
  **"工具代码不进宿主进程"这条对包内供给作废了**——它就在宿主里。换来的是简单：
  没有进程、没有协议。采用下文的生命周期简化后，禁用会从当前列表移除供给；已导入的 Python 模块
  保留在进程中直到重启，因此改源码和彻底卸载都需要重启。
- **扫描期不再知道有哪些工具**：禁用的包只占住包名，工具清单要跑起来才知道
  （问服务器，或读单例有哪些函数）。外面那一路**超时是必须的**。
- **撞名检查有三层，全在扫描期**：包名、条目名（`tools.name` / `executors.name`，写全名）。
  工具的**全名**不用判——它是 `供给名.函数名`，而供给名已唯一、一台供给内的函数名天生唯一。
  这三层的共同点是**名字全在声明里**——所以撞名从来不需要等加载。
- **`executor_ref` 里的模型那一半没了，条目名那一半换成全名**——历史 Task 里存的
  `包:模型` 要迁移到 `包.条目` 的形状（一个包可以有几条执行者）。

## 这份地图说明不了什么（欠账在哪）

上一轮的收束用的是**目录判据**：一句话说得清 · 有自己的规则 · 删掉它那条规则无处安放。
那是**结构**判据——它测不出**机制**：超时、并发、重试、保留、补偿、关停、恢复。

**机制不住在目录里，住在目录之间的缝上。** 一次"取消"要穿过
`web → gateway → tasks → core` 四个目录才成立，而每个目录单独看都是自洽的——
**所以按目录过一遍，永远是"全部通过"。**

同一条道理对"两处说法不一致"也成立：**逐份审，每一份都是对的**——
所以"这个字段必填"和"只改已存在的字段"可以在同一份文档里隔着一节打架，而两次校对都读不出来。

**所以"形状定住了"只说明每个目录自己自洽，不等于设计完整。** 机制层的欠账——连同旧代码里
发现、迁移时要一起修的缺陷——**全部记在 [`OPEN_ISSUES.md`](OPEN_ISSUES.md)**，不在这份地图里。
那份文件是一张**账单**，迁移完就该它消失。

下一轮的审法写在它开头：**不按目录审，按一次运行从头走到尾**——一次审批、一次取消、
一次重启、一次关停、一条日程跑失败，每一步都问三个问题：**这一步失败了怎么办、
这一步被重复一次怎么办、这一步没做完就断电了怎么办。**

## 契约住在哪：写这一部分的人会打开的那个文件

**不开一个集中的 `contract/` 目录**——你不会去一个叫 `contract/` 的地方找东西。

| 契约 | 住在哪 | 为什么是那儿 |
| --- | --- | --- |
| 执行者的入口函数 + 三个终态词 | `tasks/channel.py` | 包作者 **import 的就是它** |
| 执行者的 adapter | `extensions/executors.py` | 他写 `adapter.py` 时会打开这个文件 |
| 工具的句柄（`ToolSpec`） | `gateway/function/ports.py` | 保证判决的人要照着写 |
