# gateway/directory/ — **四个列表，加一个视图**

就这样，不是一个抽象概念。**能力、执行者、供应商、日程**各一个列表，外加能力列表
之上的一个视图。启动时建，读声明的时候往里注册，要用到的时候直接取。

| 文件 | 装什么 |
| --- | --- |
| `capabilities.py` | **能力列表**：有哪些工具、谁供给的、什么状态 |
| `capability_view.py` | **不是一个列表**——是能力列表之上的视图：按执行者看，声明是地板，使用方只能收紧 |
| `executors.py` | **执行者列表**：有哪些执行者、它们是什么 |
| `providers.py` | **供应商列表**：有哪些模型服务、怎么连、认识哪些模型 |
| `schedules.py` | **日程列表**：有哪些日程、什么时候跑、跑到哪 |

**为什么视图单独一个文件**：它的读者不同。看 `capabilities.py` 的人想知道"有哪些工具"；
看 `capability_view.py` 的人想知道"**为什么这个执行者看到的审批不一样**"。

## 边界

- **谁写它**：只有**加载期**（读声明那一步）。别的地方只读。
- **谁读它**：**前端**（渲染的唯一依据）、**判决**（能力 + 执行者）、
  **`tasks/` 起 worker 和派发**。别的就没有了。
- **不做判决**。它只回答"有什么、什么状态"，判决在 `function/pipeline.py`。
- **不拥有句柄**。递出去给 worker 的永远是 stub，不是能直接调的东西——见下。
- **内核不读它**。Core 不知道有哪些工具，所以这里不是任何 Port 的实现。
- **不落观测**。在线状态是运行期派生的，不写库（ADR-028）。
- **登记 ≠ 可用**。声明来自扫描（含禁用的），可用来自加载。禁用的东西在列表里
  看得见、占着名字，但没有供给——那就是"存在，但关着"。

## 四个列表，三类东西

能力、执行者、供应商都是**供给**（能调什么 / 谁负责推 / 模型在哪）；日程不是——
它是**触发**。

四个都在这里，因为**前端要渲染它们**，而"列表是前端渲染的唯一依据"这条不能有例外：
一旦有例外，前端就得另编一套概念，于是同一件事又变成两处在说。

## 建在哪：跟存储同一条规矩

**装配期决定一次，绑给需要的人**——不是 `import` 一个全局变量。

理由不是洁癖：测试需要一个**干净的例子**，而全局变量得手动清理，忘了就串味。
而且"拿到它"应该是一步看得见的事，不是一个看不见的 import。

"只有一份"这个性质两边都有；区别只在**拿到它是不是一个动作**。

## 句柄藏不藏，不是安全

我一度写过"句柄如果由供给方递出去，谁拿到谁就能调，判决就被绕过了"——**这句把威胁
模型说错了**。

真正的墙是**进程边界**：agent worker 在另一个进程里，**我们给它什么它才有什么**。
所以只要递给它的是 stub 而不是能直接调的东西，判决就绕不过去——**跟宿主内部这几个
列表藏不藏没有关系**。

宿主内部谁碰得到它们，是**设计纪律**，不是安全。

## 两个问题各答一次，别混

| 问 | 答 | 教训 |
| --- | --- | --- |
| 这个引用**能不能被解析**？ | `executors.py::exists` | 被用户停用的执行者仍要能解析，否则历史 Task 读不回来 |
| 它**能不能被新建引用**？ | `executors.py::public_configs`（过滤后） | "能不能新建"和"能不能读回"是两个问题（ADR-024） |

合成一个布尔值，一条历史记录引用了已下线的执行者，整个界面就打不开——
这个缺陷已经发生过一次。
